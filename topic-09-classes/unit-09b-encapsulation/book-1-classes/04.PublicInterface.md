# Code from Class: Designing a Small Public Interface

The **public interface** of a class is the set of methods that other code is meant to use. A good rule is:

> Make public only what the user of the class **needs**. Keep everything else internal.

The fewer ways there are to change an object, the fewer ways there are to break it.

## Example 1 — A Scoreboard

Create `04_scoreboard.py`:

```python
class Scoreboard:
    """The score of a match between two teams."""

    def __init__(self, home, away):
        self._home = home
        self._away = away
        self._home_score = 0
        self._away_score = 0

    def home_scores(self):
        self._home_score += 1

    def away_scores(self):
        self._away_score += 1

    def leader(self):
        if self._home_score > self._away_score:
            return self._home
        if self._away_score > self._home_score:
            return self._away
        return "Draw"

    def reset(self):
        self._home_score = 0
        self._away_score = 0

    def __str__(self):
        return f"{self._home} {self._home_score} - {self._away_score} {self._away}"


match = Scoreboard("Waterford", "Kilkenny")
match.home_scores()
match.away_scores()
match.home_scores()
print(match)            # Waterford 2 - 1 Kilkenny
print(match.leader())   # Waterford
```

Every attribute starts with `_`. The public interface is just five methods:

| Public method | What it does |
|---|---|
| `home_scores()` / `away_scores()` | add **one** goal |
| `leader()` | report who is winning |
| `reset()` | start again at 0 - 0 |
| `__str__()` | display the score |

**Think:** There is **no** `set_home_score()` method. What mistakes does that rule out? (Hint: could a score ever go from 2 to 7 in one step, or become `-1`?)

**Predict:** What will `print(match.leader())` show after `match.away_scores()` is called once more?

**Try it:** A referee sometimes disallows a goal. Add a method `undo_home()` that removes one home goal. It must raise a `ValueError` if the home score is already 0.

## Example 2 — Don't hand out your list

Let's record **who** scored each goal. Make these changes to `Scoreboard`:

1. In `__init__`, add `self._scorers = []`.
2. Give `home_scores` and `away_scores` a parameter `player`, and append it to the list:

    ```python
    def home_scores(self, player):
        self._home_score += 1
        self._scorers.append(player)
    ```

3. Add a method so other code can see the scorers:

    ```python
    def get_scorers(self):
        return self._scorers
    ```

Now test it:

```python
match = Scoreboard("Waterford", "Kilkenny")
match.home_scores("Aoife")
match.away_scores("Ben")

names = match.get_scorers()
names.clear()                  # outside code empties the list...
print(match.get_scorers())     # []  ...and the scoreboard's record is gone!
print(match)                   # Waterford 1 - 1 Kilkenny
```

`get_scorers()` handed out the **real** list, so outside code could change the object's data without going through any method. The score still says 1 - 1, but there are no scorers. The object no longer agrees with itself.

The fix is to return a **copy**:

```python
    def get_scorers(self):
        return list(self._scorers)     # a new list with the same names
```

**Try it:** Make the change and run the test again. Does `names.clear()` still affect the scoreboard?
