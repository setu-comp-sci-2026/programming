# Code from Class: Protecting Data with `_` and `__`

In 9a your classes checked their data **inside their methods**. For example, `withdraw()` refused to take out more than the balance. But the attributes themselves were public, so any code could still change them directly and skip the checks. In this section we close that back door.

## Example 1 — The back door

Create `03_battery.py`:

```python
class Battery:
    def __init__(self, level=100):
        self.level = level

    def use(self, amount):
        if amount <= 0:
            raise ValueError("Amount must be positive")
        self.level = max(0, self.level - amount)     # never below 0

    def charge(self, amount):
        if amount <= 0:
            raise ValueError("Amount must be positive")
        self.level = min(100, self.level + amount)   # never above 100

    def __str__(self):
        return f"Battery: {self.level}%"


phone = Battery(50)
phone.charge(80)
print(phone)        # Battery: 100%   (charge() stops at 100)

phone.level = 250   # ...but nothing stops this!
print(phone)        # Battery: 250%
```

`min(100, x)` picks the smaller of the two numbers, so the level can never go above 100. `max(0, x)` picks the larger, so it can never go below 0.

**Think:** The two methods keep the level between 0 and 100. Which line breaks that rule? Why could the class not stop it?

## Example 2 — The single underscore `_`

Replace the class in `03_battery.py` with:

```python
class Battery:
    def __init__(self, level=100):
        self._level = level          # "internal: please use the methods"

    def get_level(self):
        return self._level

    def use(self, amount):
        if amount <= 0:
            raise ValueError("Amount must be positive")
        self._level = max(0, self._level - amount)

    def charge(self, amount):
        if amount <= 0:
            raise ValueError("Amount must be positive")
        self._level = min(100, self._level + amount)

    def __str__(self):
        return f"Battery: {self._level}%"


phone = Battery(50)
phone.use(20)
print(phone.get_level())    # 30
```

A leading underscore tells other programmers: *"This is an internal detail. Use the methods instead."* Code **outside** the class should read the level with `get_level()` and change it only through `use()` and `charge()`.

**Remember:** `_` is a **convention**, not a lock. Python does not stop you:

```python
phone._level = 250      # Python allows it, but you have been warned!
print(phone)            # Battery: 250%
```

Code **inside** the class uses `self._level` freely, because that is the class's own data.

**Try it:** `Battery(250)` is still accepted. Change `__init__` so that it raises a `ValueError` if `level` is not between 0 and 100. Test it inside a `try` / `except`.

## Example 3 — The double underscore `__`

Create `03_battery_mangled.py`:

```python
class Battery:
    def __init__(self, level=100):
        self.__level = level         # two underscores

    def get_level(self):
        return self.__level


phone = Battery(50)
print(phone.get_level())     # 50
print(phone.__level)         # AttributeError!
```

**Record:** What exception do you get, and what does the message say?

Two leading underscores trigger **name mangling**. Python quietly renames `__level` to `_Battery__level`. So the attribute is still there, just under a different name:

```python
print(phone._Battery__level)    # 50
```

Name mangling makes **accidental** access harder, but it does not make the data secret. In practice most Python programmers use a single `_`, and so will we.

## Summary

| You write | Meaning | Enforced by Python? |
|---|---|---|
| `level` | public: anyone may use it | — |
| `_level` | internal: use the methods instead | No, it is a convention |
| `__level` | internal, and renamed to `_Battery__level` | Only partly |
